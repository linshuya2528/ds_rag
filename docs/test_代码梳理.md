# `test.ipynb` 代码梳理

原始 notebook 是一个从 PDF 构建本地 RAG（检索增强生成）问答的练习过程。它包含许多小实验单元和几版重复实现；整理后的可运行主线在 `test_整理版.ipynb`，原文件未改动。

## 你的代码在做什么

1. **文本清洗和 Markdown 尝试**：最前面的单元练习了 `strip()`、遍历文本行，以及按字体尺寸将 PDF 文字转换为 Markdown 标题或正文。
2. **PDF 文本提取**：用 PyMuPDF（`pymupdf`）打开 PDF，调用 `page.get_text("text", sort=True)` 逐页提取并按阅读顺序排序。
3. **文本分块**：你先用小字符串实验了切片和重叠窗口，再写了按字符固定长度切分的 `chunk_by_chars`。后续又加入“先按段落、再合并到最大长度”的方案；这更适合 RAG，因为它能保留段落语义。
4. **保存元数据**：每个分块被包装成字典，至少有 `id`、`source`、`page`、`chunk_index` 和 `text`。这些字段让回答能回溯到具体 PDF 页。
5. **向量化与存储**：`BAAI/bge-small-zh-v1.5` 把每个文本块编码成向量；Chroma 把向量、文本和元数据保存在本地 `chroma_db` 中。
6. **相似检索**：问题也被编码成向量，然后 `collection.query()` 取回最接近的问题相关文本块。
7. **重排序**：`BAAI/bge-reranker-base` 对“问题 + 候选文本块”逐对评分，将只靠向量检索得到的候选重新排序。
8. **受约束回答**：你把重排后的块拼为 `context`，在提示词中要求大模型只能使用这些资料、逐点给出来源。另有一段 JSON 校验思路，用于检查模型给出的证据是否真在检索上下文中。

## RAG 的基本框架

```text
PDF
 └─ 提取每页文本（source / page）
     └─ 清洗、按段落或字符分块（chunk_index）
         └─ Embedding 模型：文本 → 向量
             └─ Chroma：保存 向量 + 原文 + 元数据

用户问题
 └─ 同一 Embedding 模型：问题 → 向量
     └─ Chroma 相似度检索：取回候选块
         └─ Reranker 重排序：筛出最相关块
             └─ Context + Prompt → 大模型回答（附来源）
```

## 原 notebook 中的关键问题

- 多个单元反复定义了同名函数和变量（如 `chunk_by_chars`、`pages`、`source`），运行顺序不同会影响最终变量状态。
- 代码依赖前面单元产生的 `pages`、`chunk_records`、`model` 和 `collection`，从中间单元单独运行容易报错。整理版按依赖顺序排列，每一步职责明确。
- `test.ipynb` 的部分历史输出不是合法 JSON；这不影响原文件的保留，但会使某些工具或 Jupyter 无法解析它。整理版不带历史输出，使用标准 notebook 格式。
- 原始代码既有字符切分，也有段落切分。整理版采用“段落优先、超长段落回退到带重叠的字符切分”，避免把语义句子不必要地截断。
- 原代码把模型加载和检索实验散在多个单元。整理版将配置集中在顶部，之后按“建库”和“查询”两条主线组织。

## 运行顺序
